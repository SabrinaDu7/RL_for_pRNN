# pRNN width 1024 and 2048 on the production arm (2026-09-07)

## Question

Does a wider pRNN hidden state give the object-cell analysis more to find?
Before counting cells, the cheaper question this note answers: what does
width do to the run itself - prediction, the spatial representation the
policy reads, the policy - on the production multi-room arm, at the same
budget and seed as the most recent 500-wide run.

Feasibility was settled by reading before launching: the width is one config
field (`arch_prnn.hidden_size`), the fork builds the cell at that width
unrounded, every CUDA graph sizes its static buffers from the model at
capture time, and the offline tools read the width off the checkpoint. The
one literal `500` on any path is downstream:
`../experiment-curiousgeorge/src/omt/task.py` builds its OMT noise state as
`(1, 1, 500)`.

## Method

Three runs of the same config, differing ONLY in width: 8 selected rooms with
impassable objects, focal-5 CE, MLP readout, reward normalisation, seed 2,
43,936 world-model gradient steps (89,980,928 env steps), the `multienv-fast`
preset - the command line `slurm/multienv.sh` composes, with the width as a
verbatim extra flag:

    sbatch --time=03:00:00 slurm/multienv.sh true 8 2 sdu/clean-sept '' '' '' '' 0,1,2,3,5,6,7,8 h1024 --arch-prnn.loss CE --arch-prnn.focal-gamma 5 --arch-prnn.readout MLP --train-policy.normalize-reward --arch-prnn.hidden-size 1024
    sbatch --time=05:00:00 slurm/multienv.sh true 8 2 sdu/clean-sept '' '' '' '' 0,1,2,3,5,6,7,8 h2048 --arch-prnn.loss CE --arch-prnn.focal-gamma 5 --arch-prnn.readout MLP --train-policy.normalize-reward --arch-prnn.hidden-size 2048

| width | run (wandb project `curious-george-multienv` unless noted) | code | job | duration (s) | env steps/s |
|---|---|---|---|---|---|
| 500 (reference) | `mx-impassable-n8-s2-focal5mlp_curious_26-08-31-23-18-20` (`curious-george`) | `c5dd7d9` | - | 1292 | 115,396 |
| 1024 | `mx-impassable-n8-s2-h1024_curious_26-09-07-21-35-41` | `6390f87` | 10702032 | 1514 | 93,666 |
| 2048 | `mx-impassable-n8-s2-h2048_curious_26-09-07-21-35-39` | `6390f87` | 10702033 | 2260 | 56,593 |

All on Mila L40S nodes. `duration` and `FPS` are each run's own wandb
summary. The `--time` overrides were guesses made before any measurement;
the H-squared cost of the recurrence does NOT show up as wall time at these
widths because the rollout loop is launch-bound, so the launcher's default
1h30 would have sufficed.

Comparison: `curious_george.check.wandb_compare` on matched env steps, each
metric against the 500-wide reference's own adjacent-sample band
(`throwaway/2026-09-07/compare_h1024.txt`, `compare_h2048.txt`, JSON beside
each). Room-set evaluations happen every 15M env steps, so the six matched
points hold five distinct evaluations (the 25M and 37.5M columns read the
same one).

Controls: the reference's own sibling seed (`mx-impassable-n8-s3-focal5mlp`)
sits 0.05 below it on mean room sRSA at the end and outside the band at 23 of
48 points (`throwaway/2026-09-07/compare_seed_control.txt`) - the seed-to-seed
spread any width effect has to clear. A 500-wide re-run on the same code as
the width runs (`clean-sept-mx-impassable-n8-s2-focal5mlp_curious_26-09-07-05-16-40`,
local GPU) ends at 0.796, so the reference's 0.791 is not a lucky seed on old
code.

## Reading

- **Prediction improves with width, monotonically.** Lower loss at every
  matched point and at the end (0.0112 -> 0.0087 -> 0.0055). Confirmed by
  the tables above.
- **The spatial representation does not.** Both wider nets LEAD the reference
  at the first evaluation (+0.07, +0.08, outside the band) and match it
  through 50M, then slide from about 60M and end 0.12 and 0.09 below it -
  the same shape at both widths, and larger than the 0.05 the sibling seed
  moves. Pooled sRSA ends 0.12 below at both widths and pooled SWdist roughly
  doubles. MI_policy sits below the reference at 5 of 6 points at both widths.
- **Inferred, not confirmed:** this is the prediction-versus-sRSA dial seen
  before on this arm (`multienv-reward-diagnosis`, the pool-size sweep): a
  net that predicts better here represents space less spatially by these
  metrics, and width turns that dial the same way as pool size did. One seed
  per width and an unchanged learning rate, noise and sparsity fraction at
  the new widths, so the late slide could also be an optimisation effect a
  width-matched learning rate removes. Two runs cannot separate those.

## What this means for object cells

Nothing yet, and two things have to happen before a count means anything:

1. The OVC pipeline in `../experiment-curiousgeorge` assumes 500 units in two
   places: the `(1, 1, 500)` noise state in `src/omt/task.py` (would mis-size
   silently at any other width) and the chance statistic in `src/ovc.py` /
   `Q3/analyze.py`, which is phrased as "~0 of 500 units at 8+ of 28 pairs".
   The per-unit false-positive rate is unchanged, so the expected number of
   chance OVCs scales with the unit count: roughly four times as many at 2048.
2. The representation these checkpoints hold is, by sRSA, less spatial than
   the 500-wide one. More units is not more spatial units; whether it is more
   OBJECT units is exactly the open question, and the detector must be run on
   all three widths under the corrected chance statistic to answer it.

## Where things are

- Final pRNN, policy and provenance for both width runs:
  `outputs/fetched/<run name>/`. The 20-file checkpoint archives stay on Mila
  under `$SCRATCH/pRNN/multienv_<job>/outputs/<run name>/checkpoints/`.
- `Config.of_run(outputs/fetched/<run name>)` rebuilds either config exactly
  (the provenance records the effective width), and
  `throwaway/2026-09-07/rerun.py` re-trains it.
- Next runs worth their allocation, in order: a second seed at 2048; a
  learning-rate pair at 2048 (the late slide is where an optimisation effect
  would show); then the OVC detector across widths.
