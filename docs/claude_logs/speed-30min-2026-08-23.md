# Getting a full training run under 30 minutes with CUDA graphs

**Goal.** 20,480,000 environment steps in **under 30 minutes**, with sRSA,
SWdist, `pRNN loss`, `MI_policy`, `loc_entropy` and `mean SI_onPolicy` inside
the error band of `pRNN_curious_perf_optimized_26-07-08-16-04-37`.

**Method note the user set, and it governs everything below:** short runs do not
settle this. A graphed run has to go to **completion** before its metrics can be
believed - a previous attempt blew up late. No arm is called good on a partial
curve.

Gated bitwise with dropout and noise off: N sequential replays move the weights
identically to N eager `trainStep(batched=True)` calls, `max|d| 0`. Also gated:
every replay advances the weights (a graph replaying at frozen weights would

### 2. Make `on_device` address-preserving — THE UNLOCK (committed `e3c7c15`)

This is what made graphing usable at all, rather than merely fast.

`Module.to()` REPLACES `param.data`, so the cuda->cpu->cuda round trip the
spatial eval and the sample-trajectory figure sit inside left every captured
graph writing to freed memory. The old mitigation was to skip those
diagnostics under `cuda_graph` - meaning **a graphed run logged no sRSA/SWdist
at all**, which makes the metric comparison this goal is defined by impossible.

`on_device` now holds the original storages alive and copies values back into
them, so every parameter ends at the `data_ptr()` it started with. The
accelerator memory is never released and re-acquired either, so there is no
fragmentation for a re-capture to land in - which was the residual crash cause
that address DETECTION alone could not fix.

Verified in the combination that used to crash: a real training loop with
graphs on ran 8 consecutive on- and off-policy spatial evals, logging every
one. `_skip_model_move_diag` and its two tests are gone; the invariant now
lives in `on_device` and has its own test.

### 3. Graph the PPO minibatch step — WORKED (committed `2c83318`)

`update/policy` was the largest remaining stage: 2005 ms of a 3420 ms update at
`ppo_batch_size=256` (512 gradient steps on a tiny actor-critic, ~3.6 ms each
of nearly pure dispatch).

**What blocked capture, found by bisecting the region in separate processes:**
`torch.distributions.Categorical` validates its arguments by default, and
validation runs `if not valid.all()` on a device tensor - a host sync, which is
illegal during capture. With it off, every stage captures: forward, entropy,
loss, backward, `clip_grad_norm_`, capturable Adam step. Disabled around
capture only; replay runs no Python. Its eager cost is nil (3.558 ms validated
vs 3.752 unvalidated - noise).

Two address problems the world model did not have, both solved by mirroring
into static buffers: `exps` is rebuilt every update, and the minibatch indices
change every step.

**Measured: 3.558 -> 0.275 ms/step, 12.9x.**

**A wrong premise I had to correct.** The first bitwise test compared against
DEFAULT Adam and failed at 2.98e-08. Capture forces `capturable=True`, which
computes Adam's bias correction on-device in a different float32 order. The fix
was to prove that rather than loosen the tolerance: give the eager arm the same
capturable optimizer and it is exactly bitwise, with a separate test pinning
what capturable Adam alone costs.

### 5. THE BUG — a graphed run that trained on nothing, silently

This is the one worth reading. **Every arm launched before it was found is
invalid**, and every test I had passed.

**Symptom.** The graphed 20.48M-step arm (10449715) held `sRSA_onPolicy` at the
untrained floor for its whole length while its eager control reached 0.52:

```
graphed  onPolicy sRSA=0.0238  SWdist=0.0006     (start 0.033, end 0.023)
eager    onPolicy sRSA=0.5158  SWdist=0.0488
```

and the two `pRNN loss` curves agreed to three decimal places throughout. No
crash, no warning, no failing test.

**Cause.** A captured CUDA graph bakes in addresses, and `Module._apply` -
which `on_device` calls to put the model on CPU for the spatial eval -
relocates THREE kinds of tensor that need THREE different restores:

| what | what `_apply` does | how to preserve it |
|---|---|---|
| `param.data` | **replaces** the tensor | hold a reference, reassign it back |
| `param.grad` | **mutates in place** | a reference FOLLOWS it; must be DETACHED before the move |
| registered **buffers** | **replaces** the tensor | hold a reference, reassign it back |

I fixed `param.data` first (2), which is why capture stopped crashing and why
the diagnostics could be re-enabled at all. `param.grad` was the second, found
by testing across an eval. **The one that actually killed the run was the
third:** `thRNN_5win` multiplies its inputs, actions and targets by the phase
masks `inMask_f` / `actMask_f` / `outMask_f`, registered buffers read inside
`clip_mask`. With those stale, the graph scaled its inputs by whatever now
occupied that memory.

Measured, on identical data, before and after one `on_device` round trip:

```
replayed loss   0.038778 -> 0.006764     (6x drop - the inputs were being zeroed)
gradient norm     0.0603 -> 0.0156
weight delta    1.20e-01 -> 5.93e-02     (the step applied was about half)
```

**Why the forward looked fine.** The prediction loss is computed from
parameters, and those were correct. Only the masked INPUTS were wrong. So the
loss fell on a corrupted, easier problem and the curve looked healthy while the
representation never formed.

**Why every test passed.** Each one missed it a different way, and the pattern
is the lesson:

- the bitwise equivalence tests never ran a spatial eval at all
- the soak test ran 1024 episodes, where an untrained sRSA of ~0.03 is NORMAL
  and therefore indistinguishable from a dead run
- the first across-eval test I wrote covered the SERIAL path; production is
  POOLED
- `compare_metrics.py --loose` PASSED, because over 12 updates with no eval
  there is nothing to see
- the surviving assertions were "finite and changing", which a graph training
  on stranded memory satisfies perfectly

**The gate that catches it**
(`test_graphed_training_survives_repeated_spatial_evals`, parametrized over
serial and pooled): interleave evals with training and require the graphed arm
to move the weights EXACTLY as eager moves them. Confirmed to fail on the
pre-fix code, so it is not vacuous.

**Local confirmation on the config that failed**, 5.12M steps with evals every
1.024M:

```
before  sRSA  0.187 -> 0.044 -> 0.052 -> 0.052    dead
after   sRSA  0.187 -> 0.417 -> 0.269 -> 0.313    rising
```

**The generalisable lesson**, and the reason the user's "let it run to
completion" instruction was right: *a CUDA graph fails silently by
construction*. It cannot raise on a stale address; it just reads what is there.
Any assertion weaker than "identical to the eager path, on the real path, after
the real interleaving" will pass a broken graph.

### 6. Audit: what else could strand a graph's addresses

Having found one, checked the rest rather than assuming it was the only one.

- **`.to(same_device)` is address-neutral** — verified for data, grad and
  buffers. That matters because `algo.py:358/373` and `rl/collect/agent.py:51`
  call `.to(self.device)` on the hot path every update; they are no-ops.
- **Every other mover goes through `on_device`** — `evaluation/spatial.py`
  (both eval paths), `training/loop.py` (the trajectory figure),
  `evaluation/task.py`, `scripts/analysis_OMT.py`. All are fixed by the same
  change.
- **`_GraphWMTrainer._invalidate_if_moved` is kept** as defence in depth for
  anything that reassigns `param.data` outside `on_device`.
- **The policy graph has identical exposure** — the eval appends
  `agent.acmodel` to the modules it moves — and is now gated by
  `test_graphed_policy_survives_spatial_evals` on the same criterion.

(RTX 4060, `benchmark.py --updates 12 --warmup-updates 3`, fps):

```
wm_pool_group=8    33,581 -> 53,482    1.59x
wm_pool_group=1    22,256 -> 30,160    1.36x
```

The ~370 ms/update saving is IDENTICAL at both settings - only the fraction
differs, because `update/wm_train` is 203 ms at g=8 and 693 ms at g=1. That was
a requirement, and it holds structurally: `wm_pool_group` never enters
`collect_rollout`.

Gated in `tests/test_cuda_graph_rollout.py`. **Verified to have power**, not
assumed: reverting the `BatchedSRTracker` state fix turns 5 of them red. A
graph fails silently, so a gate that cannot fail is worse than no gate.

⚠️ **A graphed rollout is NOT bitwise against eager in production** - a
captured region draws from CUDA's graph-safe RNG, so the two realize different
but equally valid streams. The bitwise gate saturates the policy until the
softmax is an exact float32 one-hot, and CHECKS that assumption by requiring
every recorded `log_prob` to be exactly 0.

⚠️ **A known flaw in the perf gate, named rather than worked around:**
`compare_metrics.py --loose` FAILS on `policy_loss` at g=1 - and so do two
flag-OFF runs differing only in `exp.seed` (-0.0275 vs +0.0015). `policy_loss`
is centred on zero, so the checker's 50%-relative-mean rule measures seed noise
and will flag any zero-centred metric forever.

⚠️ **Startup grew.** A triple-graphed g8 run captures six rollout variants plus
the world-model and policy graphs before its first timestep, and shows almost
nothing on wandb for ~9 minutes - indistinguishable from a hung job. I
misdiagnosed a g8 run as regressed on this, the THIRD time I drew a conclusion
from inside g8's startup window. **Do not quote a g8 rate before 15 minutes
elapsed.**

### The budgeting flaw

10463590 and 10463591 were launched as a matched pair differing only in
`wm_pool_group`, ran for the same wall clock (24:05 vs 26:47) on the same
20,480,000 environment steps - and got **10,000 vs 80,000 world-model gradient
steps**. The comparison they were meant to support did not exist.

`rl.episodes_total` is experience, and how much TRAINING experience buys
depends on the regime. `TrainingSchedule.episodes_for_wm_steps` inverts that
through the regime; `slurm/train_fast.sh` takes the gradient-step budget as
argument 13.

### And a second, deeper one: the two budgets have different denominators

World-model steps scale with `episodes / wm_pool_group`; policy steps scale
with `updates`, i.e. with episodes alone. So **matching the world-model budget
by scaling experience UNMATCHES the policy by the same factor** - g8 at 640,000
episodes would take 2,560,000 policy steps against g1's 320,000. The fix is
`ppo_batch_size`: at 2048 instead of 256, g8 takes 64 policy steps per update
x 5,000 updates = 320,000, exactly g1's.

The genuinely matched pair (10465451 / 10465452), verified from their own
schedule lines:

```
        env steps      wm steps   policy steps   ppo_batch
g1     20,480,000        80,000        320,000         256
g8    163,840,000        80,000        320,000        2048
```

**Nothing run before this could answer whether per-gradient-step environment
averaging is worth its cost**, because no two arms had the same training
budget. This pair can.

### Cost decomposition of the g8 arm, and a correction

I estimated 2h12m for it by scaling a tqdm rate that had 100 analysis events
folded in - charging the whole run at the rollout's price. Measured properly:

```
collect/graph_step         3.3 min    <- ALL 163,840,000 environment steps
update/wm_train           17.0 min
update/policy             15.3 min    (at ppo_batch 256; ~3 at 2048)
collect/curious_rewards    2.3 min
TOTAL compute             38.6 min    -> ~27 min once the policy is matched
```

**Stepping 163.84M environment steps costs 3.3 minutes.** The rollout graph
made experience nearly free; what remains expensive is the two networks.

**At a matched budget, g8 reaches sRSA 0.7194 by 20,000 gradient steps - a level
g1 never reaches in 80,000.** Pooling wins on the axis that makes the arms
comparable. It costs 2.3x the wall clock, because it buys gradient quality by
spending 8x the experience and experience is what remains expensive.

### Speed: where the limit is, measured

```
pRNN weights 1.53 MiB, re-read every timestep -> 5.11 us memory floor
B=8 graphed:  55.0 us/timestep = 10.8x floor;  arithmetic is 0.18 us
```

**~99% overhead**, from ~40 dependent tiny kernels x 256 sequential timesteps.
Neither compute- nor bandwidth-bound. Everything we have removes LAUNCH and
DISPATCH cost; nothing reduces kernel COUNT.

- `max-autotune` gives 3.72x over default compile ALONE (60.16 -> 16.19 ms) but
  **does not compose with the CUDA graph** (13.08 vs 12.87 ms - noise): both
  remove the same overhead. It also needs the `-no-cudagraphs` variant or it
  breaks the world-model graph outright ("accessing tensor output of CUDAGraphs
  that has been overwritten"). **Rejected**: noise for ~6 min of compile.
- Only a FUSED CELL addresses kernel count. Not attempted - upstream `prnn`,
  real numerical risk.

### The instability: diagnosed, not a graphing bug

Policy collapse under `entropy_coef=0`, driven by ACCUMULATED EXPERIENCE:

```
env steps    g8 EAGER   g8 graphed        short runs (20.5M): -8% to -12%, no collapse
      20M      1.4299       1.4213        long runs (82-164M): -29% to -50%
      60M      0.5927       1.3357        MI peaks 0.72-0.85
```

**It appears in EAGER arms too** - the eager one collapses hardest (-29.1%
entropy, MI peak 0.7792). Not CUDA graphing, not pooling. The pooled regime
simply reaches it first because it spends 8x the experience.

What it is NOT: the curiosity reward flattening. `corr(entropy,
cur_reward_mean) = +0.002`. At the worst collapse point the reward and its
spread are at their HIGHEST. The likeliest mechanism is the plainest: PPO's
clipped objective has no fixed point at high entropy without an entropy term.

⚠️ Entropy is NON-MONOTONIC (smoothed min 0.3045, recovering to 0.83). Endpoint
comparisons of it, and of MI, are unreliable - see the methodology note below.

### MI: the estimator is correct, and it has a hard ceiling

`mutual_info_policy` validated against five constructed cases, exact on all:
uniform->0, deterministic-over-4-actions->2 bits, always-same-action->0,
two-halves->1 bit, and **stochastic-but-state-dependent->1 bit** (so high
entropy and high MI are NOT incompatible).

But `I(S;A) = H(A) - H(A|S)` and `policy_entropy` IS H(A|S), so with 4 actions:

```
MI <= 2 - policy_entropy       at entropy 1.82, MI can be at most 0.18
```

**You cannot ask for entropy >= 1.8 and MI >= 0.20 simultaneously.** The
2026-07 reference's band (MI 0.20-0.33 at entropy 1.34-1.55) is consistent;
`entropy_coef=0.001` pushing entropy to 1.79 mid-run puts MI against the cap.

Entropy arms so far (g8 matched, smoothed, 200-sample MA):

```
                 entropy min   MI max     entropy@163M   MI@163M
ent=0                 0.3045   0.6860           0.8306    0.3673
ent=0.001             0.7406   0.4763           1.0456    0.3659
ent 0.001->0.01       1.6226   0.1423           1.6406    0.1345
```

In flight: ramp 0->0.001 (10483973) and constant 0.0003 (10483974).

### Methodology, earned the hard way

- **wandb history is capped at 10,000 samples.** Runs of different length come
  back at different effective spacings, and the sparser one looks spikier. This
  produced a completely wrong "g8 is less stable" conclusion. `scan_history`
  fails on these runs ("Step column '_step' not found in schema"). Use
  `pN.TrainingSaver` for exact per-trial loss.
- **Never quote these metrics from a single point.** I did it three times and
  was wrong each time (sRSA 0.8533 vs 0.6711 averaged; MI "crushed to 0.06" was
  one quantile of a series averaging 0.21).
- **`benchmark.py` defaults `--sync-stages` off and `--warmup-updates` to 0.**
  Both are traps; without them attribution is wrong by up to 20x.
- **Do not quote a g8 rate before 15 minutes elapsed.** Its startup is ~9 min of
  compile+capture and it looks dead on wandb throughout. I misread this three
  separate times.
- **A CUDA graph fails SILENTLY.** Every gate must be "identical to eager, on
  the real path, after the real interleaving" - and must be PROVEN to fail when
  the code is deliberately broken. "Finite and changing" is exactly what a graph
  training on stranded memory looks like.
